# Reproducibility

The repository provides the fixed evaluation specification, experimental source code, released scoring evidence, saved aggregate results and scripts that regenerate the reported tables and figures.

## 1. Verify the files

From the repository root, run:

```sh
python verify_manifest.py
```

`REPOSITORY_MANIFEST.json` records the SHA256 hash and size of each distributed file. Git attributes preserve original line endings across platforms. Check the files before analysis; a hash mismatch should be investigated rather than bypassed.

## 2. Regenerate the reported outputs

Use Python 3.12 and the pinned dependencies:

```sh
python -m pip install -r requirements.txt
python analysis/reproduce.py
```

The script writes to a fresh `analysis/regenerated/` directory. It verifies the saved evidence bindings and nine CSV hashes, regenerates ten LaTeX tables, and compares those tables byte-for-byte with the expected outputs. It also regenerates four figure families: paired primary contrasts, descriptive reference-model contrasts, NER quality by entity type and support, and NER output-processing symptoms.

The script stops if `regenerated/` already exists. Keep or rename an earlier output directory before another run. Figure-file timestamps and platform font rendering can differ; the saved numeric evidence and expected figures support comparison.

This workflow recreates presentation outputs from the completed analysis. New model predictions and bootstrap draws are separate computational stages and are not generated by this command.

For independent score reconstruction from the released evidence, run:

```sh
python evidence/rescore.py --output ../rescored.json
```

Add `--bootstrap` to repeat the paired uncertainty calculation with NumPy. The evidence documentation identifies the released records and their scope. This process uses saved model outputs; it does not make new model or API calls. Complete KazSAnDRA review texts are not redistributed.

## 3. Check the analysis implementation

The existing software checks require no models, datasets or API access:

```sh
python -m unittest discover -s src/research_execution_20261112/final_analysis -p "test_*.py"
```

The 23 checks cover statistical kernels, boundary diagnostics, strict output handling and preservation of the primary scores when adding the prespecified fence-only sensitivity analysis. Small synthetic cases are software fixtures, not experimental observations. The two earlier assembler versions in `source_history/` are retained because these regression tests compare against them.

## 4. Dataset and evaluation identity

`src/data_manifest.json` records the original dataset repositories, revisions, file sizes and SHA256 hashes. Obtain the source files at those revisions and verify their hashes. The NER test source contains 11,307 sentences; alternative reformattings are not interchangeable with this pinned file.

`configs/PRIMARY_PROTOCOL.json` records the deterministic sampling and shared-input policy. The two `*_primary500_ids.json` files specify the exact evaluation rows. NER uses exact typed entity spans and micro-F1; sentiment uses macro-F1 over the two fixed classes, with invalid outputs retained explicitly. The analysis uses 50,000 paired text-cluster bootstrap draws, three encoder seeds, six primary contrasts and four separately identified descriptive reference contrasts.

## 5. Experimental source and reruns

`src/` preserves the internal relative module layout of the experimental project. It includes the accepted NER/SA training families, checkpoint-integrity checks, final evaluation adapters, output parsers and statistical analysis. `pilot/train_encoder.py` is the earlier 4,000-row pilot utility; the accepted full-data workflows are under `ner_training_queue01/`, `sa_training_queue01/`, `encoder_main01/` and `encoder_lr_screen02_recovery01/`.

The exact selected training and generation settings are exported in `specification/`. Running the original training or inference workflows additionally requires the pinned datasets and tokenizers, selected model weights where applicable, and machine-specific runtime bindings and evidence manifests. Runtime paths and resource admissions must be prepared for the target machine. The historical source is provided for inspection and reconstruction of the implemented method; it is not a portable one-command training package. Released records can be re-scored using `evidence/rescore.py`; complete execution traces and original request ledgers remain separate from this distribution.

The distributed checkpoint hashes identify the selected models. API templates document the demonstrations and generation settings; an API model alias is not an immutable model snapshot. Preserve model identities, raw responses, input ordering and evaluation policies when making a new run, and record any unavoidable environment or provider changes separately.
